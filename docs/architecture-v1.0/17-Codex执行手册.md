# 17 · Codex 阶段式执行手册

## 1. 为什么要按阶段推进

本项目的框架复杂度来自 Deep Agents API、插件自动发现、标准能力契约、业务权限、持久化以及 React/iframe 双模式。一次性交给 Codex “实现全部项目”容易导致编造 SDK 方法、类型分叉、空壳模块过多、将 Demo 当成真实权限。**坚持一个阶段、一个可验证产物、一个阶段报告**。

## 2. 开发前准备

1. 创建空项目或已有 Git 仓库，复制此文档包到 `docs/architecture-v1.0/` 并把 `AGENTS.md` 复制到仓库根（与已有规则冲突时先合并审核）。
2. 执行 `git status --short`，确保清楚工作区有哪些用户文件；不要擅自覆盖。
3. 首次在 Codex 开始时输入“先读 AGENTS.md + 00~03 + 当前阶段”，不要一次让 Codex把所有阶段都实现。
4. 采用主分支加阶段性工作分支或明确提交点；每次阶段修改必须输出文件变更列表。
5. 若环境不能联网、没有真实模型 key 或 DB，写 Mock/Stub 完成其余任务，并如实标明“未真实验证”。

## 3. 推荐的阶段执行顺序

```text
M0 Deep Agents POC
 └→ M1 Plugin SDK & Capability POC
     └→ M2 Agent Server + Session/Policy/SSE
         └→ M3 Shared Chat & Standalone Web
             └→ M4 React/JS/iframe SDK
                 └→ M5 独立部署与整体验收
```

## 4. 可直接复制的总控提示词

```text
你现在是这个项目的工程实施代理。请优先阅读仓库根目录 AGENTS.md，
以及 docs/architecture-v1.0/00-README.md、01-架构基线与边界.md、
02-需求追踪矩阵.md、03-工程结构与依赖规则.md 和当前阶段对应 MD。

最高约束：直接使用官方 Deep Agents；不自研 Agent Loop；
一套代码、A/B/C 各自独立部署；插件安装目录启动自动挂载；
Agent 不感知具体产品；React + Ant Design X 双 Web 模式共享 Chat Core；
服务端强制权限/脱敏/证据/审计；不可把设计中的自研接口当作已存在的依赖 API。

当前只执行【M0】（将这里的 M0 改为当前阶段）。
先检查已有代码、版本和测试，列出简短计划；然后实际实现。
如果发现官方 SDK 和文档示例冲突，以当前项目已安装版本的类型及官方文档为准，
将兼容性决策记录到 docs/implementation-status.md，不要编造接口。

交付时运行现有的 lint/typecheck/test/build 与阶段专项测试。
输出修改文件、实际测试结果、验收项、未验证项，并停止，不要自动进入下一阶段。
```

## 5. 每个阶段的指令文件

- M0：`10-M0-工程初始化与框架验证.md`
- M1：`11-M1-插件自动挂载POC.md`
- M2：`12-M2-Agent服务与会话闭环.md`
- M3：`13-M3-React独立Web与共享聊天.md`
- M4：`14-M4-嵌入助手与三类SDK.md`

建议在总控提示词后明确“本次按 `xx-Mx` 中的 T01、T02... 顺序执行”。

## 6. 对 Codex 的实现纪律

- 先**读取并使用当前仓库代码**；不重新生成已有实现、不大规模删除用户文件。
- 实现前列出本阶段核心改动点与风险；目标明确时无需重复提问。
- 设计中的 `PluginLoader`、`AgentFactory`、`definePlugin()`、`CapabilityRegistry` 是**自研名称**，要么在本阶段实现，要么定义接口并清楚标记尚未实现。
- 不要用硬编码模型回答代替真实工具调用；需要 Trace/Spy Test 证明执行路径。
- 不要在 Prompt 中硬编码具体产品名称作为业务分流条件。
- 不要把“单个用户功能测试通过”说成“生产安全完成”；严格区分 mock、集成、真实环境。
- 不引入未授权第三方库或重构整个包依赖；重大选型变更应写 ADR。
- 尽量减少新空壳目录；把阶段做成可运行、可测、可验证成果。

## 7. 发现问题后的处理

| 问题 | 处理 |
|---|---|
| 官方 SDK 参数不存在 | 写最小复现+兼容记录，使用官方替代扩展点；不伪造 |
| 模型 key 缺失 | Mock/TestDouble 跑本地逻辑，标记真实烟测未执行 |
| 数据库不可用 | 选择可替换的测试存储，保留迁移/持久化接口；不声称恢复已验证 |
| 设计文档两处冲突 | 优先已确认约束和版本化核心契约，提 ADR 并明确差异 |
| 新增范围比阶段大 | 暂缓至下一阶段，写入 backlog |
| CI 测试失败 | 先修复相关范围内错误；禁止把失败测试直接删除来通过 |

## 8. 每阶段结束报告的固定格式

```markdown

- ...
### 已实现（引用任务编号）
- ...
### 测试

- ...

- ...

- ...

```

## 9. Codex 阶段切换的人工检查

在开始下一阶段前核对：当前阶段的核心硬验收是否通过，是否对标准能力 Schema 产生未记录的不兼容修改，是否存在隐含模型密钥/原平台特殊条件分支、是否通过权限安全测试。如果没有通过，先在本阶段解决，不应通过“继续到下一阶段”掩盖缺陷。
