# 03 · Monorepo 结构、依赖规则与部署约定（V2.0）

## 1. 推荐工程结构（目标形态，按阶段渐进创建）

```text
ai-assistant/
├── AGENTS.md                      # Codex 常驻约束
├── apps/
│   ├── agent-server/              # API + Composition Root + 插件装配
│   ├── assistant-web/            # 独立 Web（聊天+少量管理）
│   ├── assistant-embed/          # iframe 助手入口
│   └── demo-host/                # React/JS/iframe 示例
├── packages/
│   ├── agent-runtime/            # 官方 Deep Agents 的薄封装
│   ├── plugin-sdk/               # 插件开发 API
│   ├── plugin-runtime/           # Manifest/Loader/生命周期
│   ├── capability-contracts/     # 旧导出的临时兼容聚合层
│   ├── contracts/                # HTTP/SSE/SDK/Views 公共协议
│   ├── assistant-ui/             # React + Ant Design X 共享 Chat Core
│   ├── assistant-transport/      # Session/Run SSE 通信
│   ├── assistant-sdk/            # React/JS API
│   └── iframe-bridge/            # postMessage 安全桥
├── core/
│   ├── capability/               # Catalog/Registry/Executor/Schema
│   ├── context/                  # Normalized Context / Snapshot
│   ├── policy/                   # 鉴权接口/强制执行策略
│   ├── evidence/                 # 数据证据标识及引用
│   └── result/                   # CapabilityResult + ViewModel
├── platform/
│   ├── model-registry/           # 当前实例薄模型配置
│   ├── session-service/          # 当前实例会话/Thread/Run
│   └── plugin-status/            # 已安装插件与状态（不重复 Registry）
├── adapters/                     # 插件源码，发布时各部署按需安装
│   ├── demo-product-a/
│   └── demo-product-b/
├── skills/                       # SKILL.md
├── domains/                      # 平台标准化的业务领域资产
│   ├── data-map/                 # 数据地图 Capability Contract
│   └── data-quality/             # 数据质量 Capability Contract
├── deploy/                       # 容器打包、裸进程 A/B 环境样例与运维说明
├── tests/                        # 契约/安全/E2E
└── pnpm-workspace.yaml
```

初期不创建空壳微服务或空包；例如 `platform/model-registry` 可以先作为 `apps/agent-server/src/modules/models/` 内部模块，未来确有复用需求再抽包。目录名是架构建议，**依赖约束比物理拆分更重要**。

## 2. 单一事实来源和代码依赖约束

1. `core/*` 不导入 `deepagents`、产品适配器、React 或管理页面。
2. `core/capability` 只定义稳定通用内核；标准 Capability 由独立 `domains/*` 领域包版本化定义，插件实现不得改变标准输入输出。
3. `plugin-sdk` 导出 `definePlugin/implementCapability` 以及公共类型；**它是自研包，不是官方 API**。
4. `adapters/*` 可依赖 `plugin-sdk`、`capability-core` 和所实现的标准能力包，不得调用 `createDeepAgent()`。
5. `plugin-runtime` 加载受信任插件、输出能力实现绑定；不持有 Agent 对话状态。
6. `agent-runtime` 可以依赖官方 Deep Agents 和 `core` 接口，不导入特定 A/B/C 插件。
7. `agent-server` 为唯一 Composition Root，负责启动时装配；不写产品名称分流 if/else。
8. `assistant-ui` 只依赖消息/展示协议，不读产品业务 API 和模型密钥。
9. `assistant-web` 与 `assistant-embed` 共用 Chat Core 与 Transport，只在 Shell 和宿主通信方式上不同。
10. 当前部署的模型/会话/凭证/插件安装目录是独立的，不跨部署共享。

`domains/*` 是业务语义的单一事实来源，不是平台运行时实现：可以依赖通用
`@assistant/capability-core`，但不得依赖 Adapter、Agent Runtime、UI 或具体产品 API。

## 3. 运行时挂载目录与源码目录不同

- `adapters/`：Monorepo 源码示例与构建位置。
- `PLUGIN_INSTALL_DIR`：当前部署**可信插件产物目录**，可以是 `/opt/ai-assistant/plugins` 或容器镜像内目录。
- 开发环境可以把构建产物复制到安装目录；**不是直接扫描所有 TS 源码并执行**。
- 未安装的插件不作为当前部署可用 Provider；M1 在启动时发现并注册。热加载不属于首版范围。

## 4. 运行配置

建议使用 `MODEL_*`、`PLUGINS_DIR`、`SERVER_*` 等当前部署配置；对产品差异保留在插件自己的环境变量/受控配置中。**不要使用 `PRODUCT_ADAPTER=product-a` 作为 Agent 业务路由逻辑**。

## 5. 部署

同一镜像/发行版可以组合不同插件产物及部署配置。A/B 两环境分别启动 Agent Server、Web、数据库/Checkpointer 与凭证，各自连接当前业务服务。即使使用同一基础设施也必须逻辑隔离数据和鉴权域。

容器发行物放在 `deploy/out/`：`pnpm pack:deploy` 把已构建的 Server、Web、Embed 和适配器产物组装到该目录，`deploy/docker-compose.yml` 按一个 `PLUGIN_ID` 启动一套实例。源码目录 `adapters/` 不作为容器内的插件扫描路径。

## 6. 工程质量

- Node LTS + pnpm + TypeScript `strict`；M0 核对并锁定实际兼容版本。
- ESLint/Prettier/Vitest，根脚本 `lint`/`typecheck`/`test`/`build`；CI 不能依赖真实模型 Key 才能通过。
- `pnpm-workspace.yaml` 按存在的包目录配置，禁止创建虚假的空功能包充数。
- 路径别名不能绕过包的 `exports` 边界；所有跨包类型来自公共入口。
