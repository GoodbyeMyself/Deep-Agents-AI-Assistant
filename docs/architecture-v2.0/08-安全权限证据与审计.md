# 08 · 安全、权限、证据与可观测性设计

## 1. 核心威胁模型

AI 助手接触业务数据、插件代码、模型与外部服务。攻击来源包括：恶意用户输入、被篡改的宿主上下文、插件供应链、工具输出 Prompt Injection、跨用户 Session ID、恶意 iframe 消息、敏感字段日志泄漏、不可信 MCP/HTTP 服务。

## 2. 强制规则（必须落在代码里）

1. **认证**：Gateway 根据当前部署的可信身份体系确认用户；前端 `getContext()` 的 `userId/permissions` 不作为授权凭据。
2. **会话隔离**：查询 Session/Run/Thread/Events/Attachments 必须校验归属、租户、有效授权；禁止只凭 UUID 读取。
3. **能力权限**：Capability Executor 在每次 Tool Call 重新验证调用权限和对象范围；模型可见性仅是辅助筛选。
4. **原平台权限继承**：Adapter 调用现有业务服务时使用可审计的真实用户身份委派或受控代理；原服务执行行/列授权及脱敏。
5. **输出脱敏**：无权读取的字段绝不返回模型；后端对 Tool Result 和前端输出二次过滤。
6. **插件可信**：只加载审核通过、路径规范、哈希/来源可信的安装包；模块加载不是沙箱；默认禁用运行时任意 JS 上传。
7. **Skills/Prompt Injection**：网页内容、数据库字段备注、Skill 外部材料都可包含恶意指令；作为不可信数据处理，不得提升权限/重写系统规则。
8. **管理接口**：模型 Secret/平台配置/插件启停与 Agent 配置仅管理员有权；凭证只保存引用，日志不可打印明文。
9. **审批**：平台统一允许已批准且有业务权限的 read 查询直接执行；write 和 destructive 强制用户二次确认后执行，并保持幂等保护。规则由平台服务端定义，不能由 Prompt、UI Context 或 MCP 配置关闭（ADR-039、ADR-041）。

### E3 Skill 安全补充

- `SKILL.md` 是不可信指令载荷，即使来自批准 Bundle，也不能修改可信 Runtime Context、Policy、Credential Provider 或 Evidence。
- Skill 的 Tool 依赖必须属于同一插件，或由部署使用 `<skillPluginId>-><capabilityId>@<version>` 明确批准；缺少绑定时 Skill 排除。
- 凭证依赖只通过 `hasCredential(pluginId, reference)` 检查存在性，不读取或记录密钥；未配置检查器时需要凭证的 Skill 默认排除。
- Skill 目录拒绝路径逃逸、任意层级符号链接、异常文件类型和超限内容；加载前生成内容哈希，装配时复制到隔离快照。
- 同名 Skill 固定拒绝覆盖。Skill 可见性不能替代 Executor 的逐调用授权，权限不足仍返回 `FORBIDDEN`。

### E4 元数据查询安全补充

- `data_map.get_object_metadata` 的能力级权限只允许进入查询流程，不能替代原业务对象级、字段级授权。
- Adapter/原业务 API 必须在结果进入 Executor、模型上下文、SSE 或日志前移除无权字段；不得只靠 UI 隐藏。
- 部分字段不可见时返回 `partial` 与泛化 warning，不在 warning/Evidence 中泄露受限字段名称或值。
- Metadata Evidence 只记录授权后对象、方法和服务端引用句柄；引用解析仍需再次鉴权。

## 3. 审计字段最小集合

```ts
interface AuditRecord {
  id: string;
  timestamp: string;
  traceId: string;
  userId: string;
  tenantId?: string;
  sessionId?: string;
  runId?: string;
  action: "prompt" | "tool" | "model" | "session" | "admin" | "error";
  capabilityId?: string;
  pluginId?: string;
  contractVersion?: string;
  targetObjectIds?: string[];
  dataScope?: Record<string, unknown>;
  outcome: "success" | "partial" | "denied" | "error";
  evidenceRefs?: string[];
  errorCode?: string;
}
```

保存用户提问/模型回答必须遵循业务脱敏与日志保存制度；建议按必要性设置正文加密、脱敏索引、保留期和访问角色，避免把所有敏感明文写入普通日志。

## 4. Evidence & Claims

- Source Evidence 由执行器从真实业务响应提取，记录数据对象、时间、过滤范围、统计口径、抓取时间和服务端引用句柄。
- 引用解析须再次授权；不生成公开可分享的敏感数据长 URL。
- 结论按 `observed / inferred / unknown` 分级；缺少因果证据时只说明“可能原因”，不得写“已证实”。
- 返回 `partial` 的结果应在 UI 中明显标识缺失范围与不能判断的部分。

## 5. HTTP/iframe 安全

- CSP 的 `frame-ancestors` 精确限制宿主源；不使用 `*` targetOrigin；校验 Message origin/source/schema/channelId。
- 限制 CORS、CSRF（取决于 Cookie/Bearer 方案）、请求体大小、上传文件类型及数量；默认 HTTP API 只对受信任来源开放。
- 模型密钥、业务长期令牌不得进入 iframe URL 或客户端 localStorage；建议使用短期嵌入票据交换服务端 Session。
- SSE 重连需要用户认证和 Session/Run 归属检查，绝不以 `Last-Event-ID` 作为授权依据。

## 6. 上传、工具与插件输出限制

- 文件上传按部署配置限制大小、类型、数量，存储安全扫描后再做内容解析，附件 ID 与用户/会话绑定。
- ToolResult 标记来源为不可信数据，防止业务字段中的“忽略规则”文本当作高优先级指令。
- 对外 HTTP/MCP 配置限制可访问 Host、端口、超时、重定向和代理；防止 SSRF。
- 查询规模限制、执行时长、工具调用次数有统一上限；避免无限 Token 成本与上游 API 过载。

## 7. 测试用例（强制）

| 反例/攻击                       | 预期                               |
| ------------------------------- | ---------------------------------- |
| 前端传 `userId=admin`           | 忽略，按服务端身份执行             |
| 用户 A 拿到用户 B `threadId`    | 403/404，数据不泄漏                |
| 模型请求不存在的业务对象        | 业务层授权/不存在处理；不凭空回答  |
| 插件返回未授权 PII              | 强制过滤/拒绝，记录审计            |
| 插件 Manifest `../../etc/...`   | Loader 拒绝                        |
| 任意未批准 JS 插件              | 不加载、不执行                     |
| Tool 结果包含“输出 API KEY”     | 作为普通数据，不改变 Agent 权限    |
| Skill 指示绕过权限或调用未关联 Tool | 忽略权限指令；未关联声明拒绝装载 |
| Skill 所需 Tool/配置/凭证缺失   | Skill 排除，Capability 状态可独立保持 |
| SSE 用户改 `runId`              | 再次授权，拒绝访问他人事件         |
| iframe 非白名单 origin 发送消息 | Host/Child 拒绝并审计              |
| 数据缺失三天/口径冲突           | `partial`，有 warnings，无伪造数据 |

## 8. 可观测性

日志要统一 `traceId`/`sessionId`/`runId`/`toolCallId`/`capabilityId`/`pluginId`；采集运行耗时、模型/token 用量、工具成功率、上游超时、Schema 校验失败、权限拒绝、SSE 断流/恢复、插件健康。可接入 OpenTelemetry/LangSmith 作为增强，但不影响基本审计持久化。

## MCP 工具执行与二次确认（ADR-041）

平台唯一策略入口为 packages/mcp-client-runtime/src/tool-execution-policy.ts：read → execute，write/destructive → confirm；策略对象冻结，未知风险拒绝执行，不提供关闭写确认的环境开关。

平台先校验部署批准的 Server、Tool、Schema 摘要、风险和 MCP annotations 一致性，再由 Tool Factory 对每次调用应用此策略。HTTP 与开发 stdio 均注入 apps/agent-server/src/modules/mcp/tool-confirmation.ts 的同一处理器；缺少处理器时不能暴露写工具。

确认处理器使用官方 LangGraph interrupt，持久化后经既有 AG-UI interrupt outcome 送达界面。展示工具、操作风险和准确参数；用户经受控 resume 提交确认/拒绝。服务端检查会话归属、待审批状态及恢复幂等性，客户端不能通过 resume 替换工具或参数。普通聊天“已确认”、模型提供 approved 字段、缺少有效确认回执均不能执行写入。

AG-UI 是确认交互协议，不能替代服务端策略。原业务权限由 MCP/原业务接口逐调用执行；二次确认不授予额外权限。MCP 只声明业务工具风险，校验平台确认断言并防重复执行，不定义平台是否弹出确认的策略。

新增 MCP 无需实现自己的审批界面，按平台治理协议声明风险并获得部署批准即可使用统一确认链路。需要写入的 HTTP MCP 仍须接入受支持的可信身份与确认断言；stdio 只用于开发且生产环境仍禁止。
