## ADR-020：部署未提供能力时使用 `UNSUPPORTED`

- 问题：Capability Catalog 可以声明平台标准契约，但某个独立部署不一定安装对应 Provider。原实现返回可重试的 `PROVIDER_UNAVAILABLE`，会让调用方误以为重试即可恢复。
- 决定：Catalog 已知但当前 Capability Registry 没有绑定时返回不可重试的 `UNSUPPORTED`。Provider 已安装但其上游临时不可用时，仍可由 Adapter 返回 `PROVIDER_UNAVAILABLE` 或 `UPSTREAM_*`。
- 影响：只调整标准错误语义，不改变 Catalog、Plugin Loader、Tool Factory 或 Agent Loop；Capability Audit 同步记录 `UNSUPPORTED`。
- 回滚：恢复 Executor 的旧映射和测试即可，不涉及数据迁移。
- 测试：Registry/Executor 单测必须断言未绑定能力返回 `UNSUPPORTED`；Adapter 的上游故障仍由各自契约测试覆盖。

## ADR-021：iframe 悬浮容器由声明式 Loader 统一提供

- 问题：Product A/B 曾分别实现悬浮按钮、固定面板、iframe、加载状态和响应式 CSS，导致接入方承担助手 UI，并产生跨框架重复代码。
- 决定：Assistant Embed 发行稳定的 `assistant-loader.js`。Loader 在 Shadow DOM 内创建并维护悬浮按钮、固定面板和 iframe，复用受信任 Bridge；业务入口 HTML 只配置 iframe URL、Ticket Endpoint、初始 Context 和非敏感外观参数。
- 安全：生产 Ticket Endpoint 根据宿主可信登录态签发一次性 Ticket；长期凭证、模型 Key 和业务 Token 不进入 HTML。Loader 继续校验 Origin、Window Source、channelId 和消息 Schema。Demo Token 仅允许 localhost。
- Context：初始 Context 可声明在入口 HTML；页面对象变化通过标准事件更新下一次请求，运行中的 ContextSnapshot 不改变。
- 影响：Product A/B 删除各自的助手 JSX/Vue 模板、Bridge 生命周期和悬浮 CSS；独立 Web 与 Shared Chat Core 不变。
- 测试：Loader 单测覆盖挂载、开关、Context 更新和销毁；A/B 浏览器测试覆盖同一 Loader、固定定位、安全握手和对象切换。

## ADR-022：稳定 Core + 可信动态 Capability Contract 注册

- 问题：当前 Plugin Runtime 可以动态发现和注册 Provider，但 `KnownCapabilityContract` 与 `standardCapabilityContracts` 在 Core 编译期封闭列举具体能力。新增能力仍需修改 Core、多层导出和整套发行版，未达到“安装一个插件包并重启即可增加能力”的扩展目标。
- 备选一：继续使用封闭 Catalog。优点是治理简单，缺点是所有能力开发都要求平台发版，Plugin 只能替换已知能力实现。
- 备选二：允许任意插件自行定义任意契约、权限和风险。优点是扩展最快，缺点是会产生同名不同义、权限自授予和不可信 Tool Schema，违反企业集成定位。
- 决定：采用混合模型。Core 只保留通用 `CapabilityContract`、`CapabilityResult`、Context、Policy、Evidence、Audit 和注册执行规则；具体能力可以从受信任来源动态注册。标准能力由独立、版本化的平台契约包提供；部署私有能力可由批准的可信本地 Plugin Bundle 携带。
- 标准命名空间：`data_map.*`、`data_quality.*` 等平台已发布命名空间为保留空间，只能引用平台批准的标准契约包，插件不能用自带 Schema 覆盖同 ID、同版本契约。新增保留命名空间须通过 ADR 或架构基线变更。
- 私有命名空间：使用至少三段的 `<organization>.<domain>.<action>` 形式，例如 `acme.order.get_risk_summary`。组织前缀必须进入当前部署允许列表；私有契约不得声明为平台标准能力。
- 信任边界：首个动态契约版本只接受当前部署批准、路径和哈希校验通过的 Local Plugin Bundle。HTTP Provider 只能实现服务端已注册的标准契约，不能通过远端响应临时定义 Tool Schema。插件模块仍是可信同进程代码，不宣称沙箱。
- 权限与风险：插件可以声明 `requiredPermission` 和 `riskLevel`，但声明不构成授权。当前只读 MVP 的动态能力只允许 `riskLevel=read`；权限名、命名空间和凭证引用必须由部署策略批准。`write/high` 需后续独立 ADR、人工审批和幂等设计后才能开放。
- 冲突与原子性：相同 `id + version` 的重复契约、不同 Schema、重复 Provider、Tool 名归一化冲突均失败关闭。Plugin Bundle 的 Contract、Provider 和 Skill 在 staging 中完成校验后原子提交；失败不得留下半注册状态。
- Skill：Plugin Bundle 可以携带 Skill，但 Skill 只描述何时和如何使用已批准 Tool，不能注册权限、改变身份、提供凭证或绕过 Capability Executor。Tool 缺失或无权时关联 Skill 不得使调用成功。
- 运行一致性：Manifest V1 至少保留一个迁移周期。当前 Agent/Run 使用创建时固定的 Tool/Skill Snapshot；首版插件变化仍需重启生效，不做热加载。
- 部署边界：A/B/C 继续独立部署、独立批准插件和凭证；动态注册不引入跨实例 Catalog、会话或配置同步。
- 依赖影响：E1 开放 Capability SDK 与动态 Catalog；E2 实现 Manifest V2 和事务装载；E3 接入插件 Skill；E4 拆分标准能力包并迁移 A/B Adapter。不得修改或 Fork Deep Agents Agent Loop。
- 迁移：先保留静态 Catalog 兼容来源，再引入 Manifest V2，之后迁移现有标准能力，最后按废弃周期移除固定联合类型。未安装 Provider 继续返回 `UNSUPPORTED`。
- 回滚：E1 可恢复静态 Catalog；E2 可关闭 Manifest V2 并只加载 V1；E3 可关闭插件 Skill 而保留 Tool；E4 可临时恢复旧契约导出。所有回滚保持现有能力 ID 和版本不变。
- 测试：E0 固定 Catalog、Manifest V1、A/B Provider、Tool 名、权限拒绝、Evidence、未批准插件、未知契约和路径逃逸基线；E1～E5 逐步增加动态契约、命名空间、Schema 冲突、事务回滚、Skill/Tool 关联和升级兼容测试。
- E1 实施记录（2026-10-19）：Core/Plugin SDK 已开放通用 `defineCapability()`，Catalog 已支持携带 `platform/plugin` 来源的原子 `register/registerMany`。插件来源契约在内核层执行三段式私有命名空间、平台保留空间、只读风险、权限格式及 Zod Schema 校验；重复 `id + version` 和 Tool 名归一化冲突失败关闭。标准契约继续作为平台来源注册，Manifest V1 不变；插件包贡献契约、部署允许列表接入和跨 Contract/Provider 的事务提交仍留在 E2。
- E2 实施记录（2026-10-20）：Manifest V2 仅允许已批准的可信 Local Bundle 贡献私有只读 Contract；插件 ID、命名空间和权限均由部署显式批准。Manifest、运行时 Contract、Provider 与 Catalog 来源必须一致。Catalog/Registry 使用注册租约，在 Provider 冲突、初始化或健康失败时同步回滚；V1 Local/HTTP 保持兼容。V2 Skill 路径已做真实路径、根目录和符号链接校验，但 Skill 内容与 Agent 装配仍留在 E3。
- E3 实施记录（2026-10-20）：Manifest V2 Skill 对象声明以 Capability/配置/凭证依赖作为装配门禁；依赖缺失时 Skill 排除而 Tool 可独立保留。Plugin Skill Registry 对同名采用 `deny`，冲突 Bundle 回滚；批准的跨插件依赖必须显式列入部署策略。经路径、目录树、frontmatter、Tool 关联与内容哈希验证的 Skill 被复制到隔离的启动快照，再通过官方 Deep Agents `skills` + `FilesystemBackend` 装配；当前 Agent 不刷新安装目录。Skill 与外部引用始终是不可信指令，不能形成授权或 Evidence，Executor 仍逐调用拒绝无权限主体。
- E4 实施记录（2026-10-20）：`core/capability` 更名为纯通用 `@assistant/capability-core`，具体标准 Schema 迁移至 `@assistant/capability-data-map` 与 `@assistant/capability-data-quality`。旧 `@assistant/capability-contracts` 作为独立聚合兼容层保留至 E5 后首个发布周期，最早在下一次 breaking release 移除。新增 `data_map.get_object_metadata@1.0.0` 未在 Core、Agent Runtime、Tool Factory 或 UI 增加能力 ID 分支；A/B Adapter 在原始字段不同的前提下通过同一契约套件，并在模型可见结果前执行对象/字段授权和敏感字段过滤。
- 目录归属调整（2026-10-20）：标准业务契约包的 npm 名称与协议保持不变，源码从 `packages/capability-*` 迁移到 `domains/data-map` 与 `domains/data-quality`。`packages/` 仅承载平台技术组件，`domains/` 承载跨产品复用的业务语义；本调整不改变 Capability ID、Schema、权限或运行时装载机制。

## ADR-023：本地版本化插件发布与显式批准

- 问题：Manifest V2 已能安全装载 Contract/Provider/Skill，但仅靠手工复制无法稳定证明构建产物、批准记录、升级兼容与回滚版本一致。
- 决定：发布器只处理本地、已构建、可信 Manifest V2 Bundle。入口 SHA-256 写入 Manifest；部署批准文件显式绑定插件 ID、命名空间、权限、产物哈希和配置快照版本。安装目录分为 active、不可变 release 和非敏感 state，实例仍在重启时发现插件。
- 升级：默认必须保留上一版本的全部 `capabilityId@contractVersion`。breaking 变更需要发布元数据与部署批准双向允许。配置迁移在安装前由受审查的实例运维步骤完成，发布器只校验版本兼容，不执行 Bundle 提供的迁移代码。
- 安全：发布器不远程下载、不接收在线上传、不读取密钥、不热加载，也不把 Plugin Skill 当授权。Runtime 继续执行路径、Schema、权限、风险、Skill 与事务注册门禁；原业务 API 和 Evidence Resolver 继续执行最终授权。
- 失败与回滚：哈希、批准、契约或配置兼容失败发生在 active 切换前；已验证 release 保留用于回滚。禁用只移除 active 可发现副本，不删除 release/state。所有操作在停止新 Run 后执行并重启实例。
- 测试：E5 覆盖模板生成、哈希篡改、配置兼容升级、失败不切换、回滚/禁用诊断，以及 A/B 独立实例安装相同标准能力和不同私有能力；E0～E4 负面测试作为完整门禁继续执行。

## ADR-024：AG-UI 1.0 事件兼容层与可选 CopilotKit Shell

- 问题：当前版本化 Assistant SSE 已具备身份隔离、持久 Run、事件重放、Evidence 和受控 View，但事件载荷仍是项目私有格式，消息生命周期和 Tool/Subagent 事件难以被其他 Agent 前端直接复用。
- 决定：锁定 `@ag-ui/core@1.0.3`、协议版本 `1.0`，将 AG-UI 作为 Agent 交互事件的兼容基线。先从已持久化的 `AssistantEvent` 做确定性投影，不替换现有事件源、REST 资源或默认传输端点。
- 企业扩展：Evidence 使用 `CUSTOM(name=enterprise.evidence.added.v1)`，受控 View 使用 `CUSTOM(name=enterprise.view.created.v1)`；扩展载荷继续由平台 Zod Schema 严格验证。`eventId/sequence/sessionId/schemaVersion` 写入 `enterprise-assistant` metadata，AG-UI 保留命名空间不被占用。
- 安全：AG-UI `RunAgentInput` 的 `threadId/runId/tools/context/state/forwardedProps` 均不得直接成为可信身份、权限、Tool 集合或 ContextSnapshot。浏览器仍只通过 Gateway 创建受控 Run；原业务授权、Capability Executor、Evidence 再鉴权和 iframe 边界不变。禁止把 LangGraph raw event、Tool 参数或原始业务结果直接投影到客户端。
- 前端：现有 Ant Design X Shared Chat Core 保持默认实现。CopilotKit 只能通过独立 Adapter/Shell 接入同一 AG-UI 端口，不进入 `assistant-ui` 核心依赖，不与现有 ChatStore 形成双状态源；默认不得要求 CopilotKit Cloud。
- 迁移：POC 阶段保持旧协议；完成映射契约、安全负面和确定性重放测试后，再增加双协议端点及 ChatAgentPort。只有在断流重放、取消、Context 固定、Evidence、A/B 和 iframe 回归全部通过后才允许切换默认事件消费格式。
- 回滚：移除 AG-UI 投影与可选 Adapter 即可恢复旧事件消费；现有持久事件、Session、Run、ContextSnapshot 和 Evidence 数据无需迁移。
- 测试：必须覆盖文本 start/content/end、Tool 安全摘要、Subagent、成功/失败/取消终态、企业 Custom Schema、敏感字段不出站和同一持久事件重复投影完全一致。
- 双协议端点实施记录（2026-10-20）：新增 `/api/v1/runs/{id}/ag-ui/events`，从同一已鉴权 `AssistantEvent` 日志投影，不创建第二个 Run。AG-UI 游标编码源事件和投影子序号，断在一个源事件展开的多个标准事件之间仍可精确续传；错误游标返回 `EVENT_CURSOR_EXPIRED`。`ChatAgentPort<TEvent>` 隔离 Shell 与具体 Transport，现有 Chat Core 保持旧事件，AG-UI 端口作为并行实现。
- 标准命令入口实施记录（2026-10-21）：新增 `POST /api/v1/ag-ui`，使用官方 `RunAgentInput` Schema，并将请求收敛到已有 Session、已鉴权 ContextSnapshot、幂等 Run 和同一 AG-UI 投影流。`threadId/runId` 不建立身份；`context/state` 不参与授权；客户端 Tool、非文本内容和 interrupt resume 当前失败关闭。公开 AG-UI 生命周期保留调用方 `runId`，服务端事实 Run 仍由平台生成和持久化。该入口不引入 CopilotKit Runtime/Cloud，也不切换默认 Shell。
- 可选 Shell Spike 实施记录（2026-10-21）：新增隔离的 `apps/copilotkit-shell-spike`，使用 CopilotKit v2 `CopilotChat` 和开发期本地 `HttpAgent`，先经既有 REST 创建 Session/ContextSnapshot，再调用同一 `POST /api/v1/ag-ui`。CopilotKit 不进入 `assistant-ui`、不成为默认 Shell、不注册客户端 Tool，也不引入 Cloud/Runtime。`@copilotkit/react-core@1.79.1` 内置 AG-UI 客户端 1.0.2，而服务端与直接验证客户端锁定 1.0.3；当前仅接受协议 1.0 线级兼容，不把包类型或实现版本视为统一。当前生产构建主产物约 2.04 MB（gzip 586 KB）且包含大量 Markdown/代码高亮资源，未满足默认 Shell 的性能预算；保持可选和隔离。
- AG-UI 取消桥接实施记录（2026-10-21）：`POST /api/v1/ag-ui` 的响应流被客户端提前取消时，服务端使用创建该流时已认证的 principal 和内部 Run ID 调用既有 `AgentRunner.cancel`。客户端 `runId` 不参与资源定位，内部 Run ID 不向 CopilotKit 暴露；普通 GET 重放流断开不会取消 Run。Node HTTP 适配层显式把连接提前关闭传播到 Web Stream cancel，官方 `HttpAgent.abortRun()` 因而可终止 durable run。该语义已通过真实本地 HTTP 连接的断流测试；尚未形成 CI 浏览器 STOP 点击回归。
- 默认 Shared Chat Core 切换记录（2026-10-21）：Ant Design X 继续作为默认渲染层，`assistant-ui` 的单一 ChatStore 改为消费 `AgUiEvent`，覆盖文本、Tool、Subagent、成功/失败/取消和经项目 Schema 校验的 Evidence/View `CUSTOM` 事件。默认创建 Run、状态查询、显式取消、Session、ContextSnapshot 和 Evidence 仍走企业 REST，再由 `AgUiChatAgentPort` 读取同一内部 Run 的 `/ag-ui/events` 投影；不改用 `POST /ag-ui`，因此内部 Run ID、精确重连和刷新恢复语义不变。旧 `AssistantEvent` 端点作为兼容/回滚路径保留，CopilotKit 仍不进入核心依赖。
