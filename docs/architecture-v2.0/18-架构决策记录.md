## ADR-020：部署未提供能力时使用 `UNSUPPORTED`

- 问题：Capability Catalog 可以声明平台标准契约，但某个独立部署不一定安装对应 Provider。原实现返回可重试的 `PROVIDER_UNAVAILABLE`，会让调用方误以为重试即可恢复。
- 决定：Catalog 已知但当前 Capability Registry 没有绑定时返回不可重试的 `UNSUPPORTED`。Provider 已安装但其上游临时不可用时，仍可由 Adapter 返回 `PROVIDER_UNAVAILABLE` 或 `UPSTREAM_*`。
- 影响：只调整标准错误语义，不改变 Catalog、Plugin Loader、Tool Factory 或 Agent Loop；Capability Audit 同步记录 `UNSUPPORTED`。
- 回滚：恢复 Executor 的旧映射和测试即可，不涉及数据迁移。
- 测试：Registry/Executor 单测必须断言未绑定能力返回 `UNSUPPORTED`；Adapter 的上游故障仍由各自契约测试覆盖。

## ADR-021：iframe 悬浮容器由声明式 Loader 统一提供

- 问题：Product A/B 曾分别实现悬浮按钮、固定面板、iframe、加载状态和响应式 CSS，导致接入方承担助手 UI，并产生跨框架重复代码。
- 决定：Assistant Embed 发行稳定的 `assistant-loader.js`。Loader 在 Shadow DOM 内创建并维护悬浮按钮、固定面板和 iframe，复用受信任 Bridge；业务入口 HTML 只配置 iframe URL、Ticket Endpoint、初始 Context 和非敏感外观参数。
- 安全：生产 Ticket Endpoint 根据宿主可信登录态签发一次性 Ticket；长期凭证、模型 Key 和业务 Token 不进入 HTML。Loader 继续校验 Origin、Window Source、channelId 和消息 Schema。Demo Token 仅允许 localhost。
- Context：初始 Context 可声明在入口 HTML；页面对象变化通过标准事件更新下一次请求，运行中的 ContextSnapshot 不改变。
- 影响：Product A/B 删除各自的助手 JSX/Vue 模板、Bridge 生命周期和悬浮 CSS；独立 Web 与 Shared Chat Core 不变。
- 测试：Loader 单测覆盖挂载、开关、Context 更新和销毁；A/B 浏览器测试覆盖同一 Loader、固定定位、安全握手和对象切换。

## ADR-022：稳定 Core + 可信动态 Capability Contract 注册

- 问题：当前 Plugin Runtime 可以动态发现和注册 Provider，但 `KnownCapabilityContract` 与 `standardCapabilityContracts` 在 Core 编译期封闭列举具体能力。新增能力仍需修改 Core、多层导出和整套发行版，未达到“安装一个插件包并重启即可增加能力”的扩展目标。
- 备选一：继续使用封闭 Catalog。优点是治理简单，缺点是所有能力开发都要求平台发版，Plugin 只能替换已知能力实现。
- 备选二：允许任意插件自行定义任意契约、权限和风险。优点是扩展最快，缺点是会产生同名不同义、权限自授予和不可信 Tool Schema，违反企业集成定位。
- 决定：采用混合模型。Core 只保留通用 `CapabilityContract`、`CapabilityResult`、Context、Policy、Evidence、Audit 和注册执行规则；具体能力可以从受信任来源动态注册。标准能力由独立、版本化的平台契约包提供；部署私有能力可由批准的可信本地 Plugin Bundle 携带。
- 标准命名空间：`data_map.*`、`data_quality.*` 等平台已发布命名空间为保留空间，只能引用平台批准的标准契约包，插件不能用自带 Schema 覆盖同 ID、同版本契约。新增保留命名空间须通过 ADR 或架构基线变更。
- 私有命名空间：使用至少三段的 `<organization>.<domain>.<action>` 形式，例如 `acme.order.get_risk_summary`。组织前缀必须进入当前部署允许列表；私有契约不得声明为平台标准能力。
- 信任边界：首个动态契约版本只接受当前部署批准、路径和哈希校验通过的 Local Plugin Bundle。HTTP Provider 只能实现服务端已注册的标准契约，不能通过远端响应临时定义 Tool Schema。插件模块仍是可信同进程代码，不宣称沙箱。
- 权限与风险：插件可以声明 `requiredPermission` 和 `riskLevel`，但声明不构成授权。当前只读 MVP 的动态能力只允许 `riskLevel=read`；权限名、命名空间和凭证引用必须由部署策略批准。`write/high` 需后续独立 ADR、人工审批和幂等设计后才能开放。
- 冲突与原子性：相同 `id + version` 的重复契约、不同 Schema、重复 Provider、Tool 名归一化冲突均失败关闭。Plugin Bundle 的 Contract、Provider 和 Skill 在 staging 中完成校验后原子提交；失败不得留下半注册状态。
- Skill：Plugin Bundle 可以携带 Skill，但 Skill 只描述何时和如何使用已批准 Tool，不能注册权限、改变身份、提供凭证或绕过 Capability Executor。Tool 缺失或无权时关联 Skill 不得使调用成功。
- 运行一致性：Manifest V1 至少保留一个迁移周期。当前 Agent/Run 使用创建时固定的 Tool/Skill Snapshot；首版插件变化仍需重启生效，不做热加载。
- 部署边界：A/B/C 继续独立部署、独立批准插件和凭证；动态注册不引入跨实例 Catalog、会话或配置同步。
- 依赖影响：E1 开放 Capability SDK 与动态 Catalog；E2 实现 Manifest V2 和事务装载；E3 接入插件 Skill；E4 拆分标准能力包并迁移 A/B Adapter。不得修改或 Fork Deep Agents Agent Loop。
- 迁移：先保留静态 Catalog 兼容来源，再引入 Manifest V2，之后迁移现有标准能力，最后按废弃周期移除固定联合类型。未安装 Provider 继续返回 `UNSUPPORTED`。
- 回滚：E1 可恢复静态 Catalog；E2 可关闭 Manifest V2 并只加载 V1；E3 可关闭插件 Skill 而保留 Tool；E4 可临时恢复旧契约导出。所有回滚保持现有能力 ID 和版本不变。
- 测试：E0 固定 Catalog、Manifest V1、A/B Provider、Tool 名、权限拒绝、Evidence、未批准插件、未知契约和路径逃逸基线；E1～E5 逐步增加动态契约、命名空间、Schema 冲突、事务回滚、Skill/Tool 关联和升级兼容测试。
- E1 实施记录（2026-10-19）：Core/Plugin SDK 已开放通用 `defineCapability()`，Catalog 已支持携带 `platform/plugin` 来源的原子 `register/registerMany`。插件来源契约在内核层执行三段式私有命名空间、平台保留空间、只读风险、权限格式及 Zod Schema 校验；重复 `id + version` 和 Tool 名归一化冲突失败关闭。标准契约继续作为平台来源注册，Manifest V1 不变；插件包贡献契约、部署允许列表接入和跨 Contract/Provider 的事务提交仍留在 E2。

## 变更基线记录

### V2.0 / 2026-10-13

- 由“通用 AI Agent 平台”收敛到“企业业务智能体集成框架”。
- 明确四个核心业务目标：Capability、Policy、Context、Evidence；**Plugin 自动挂载保留为核心扩展机制**。
- 去掉面向 OpenClaw 式产品生态的高优先级计划：插件市场、多渠道 Gateway、跨实例会话和复杂通用配置。
- 重新编写 M0～M5；允许从新版 M0 重做，但要求 Codex 保护未授权文件和数据。

## 未来变更流程

新增关键技术选型或修改核心契约时，提交一个独立 ADR：问题→备选→决定→依赖影响→迁移/回滚→测试要求。不得在某个阶段悄悄扩大范围。
