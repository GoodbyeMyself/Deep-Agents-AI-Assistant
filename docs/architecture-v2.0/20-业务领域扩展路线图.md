## 2. Agent 与 Skill 划分原则

- **标准 Capability** 是可验证的业务接口；普通检索/汇总不必每次委派子智能体。
- **专业 Subagent** 仅在需要多步分析、涉及多个 Tool 或知识深度要求高时创建，并且限制工具列表。
- **Skill** 只提供领域方法（如质量趋势分析、字段标准匹配、血缘证据使用），不能代替 Tool 调用或原业务授权。
- 插件可以声明自己提供哪些能力和推荐技能，但不直接篡改主 Agent 的 Prompt 与高权限工具集合。

## 3. 建议的业务实施波次（MVP 之后）

### P1：数据质量深度分析与数据地图完善

补充质量明细、规则统计、问题分布、趋势比较、复发统计、对象关系；引入来源追溯视图。质量问题原因必须分为“事实/推测/无法判断”，并保留统计口径。

### P2：数据标准与数据血缘

标准建议基于字段名、注释、可授权样例和匹配规则；识别同名不同义等冲突。血缘推断记录 SQL/任务依赖/字段证据，附推断状态与可复核依据，不把候选当作事实。

### P3：数据服务建议与工单辅助

形成资产推荐、服务说明/参数/返回结构/测试草稿，识别相似服务和口径冲突；服务运行支持异常、高频、容量风险的建议；工单支持历史检索和风险提示。

### P4：更强的 Agent 协作与高级平台治理

按需要增加专业子智能体、动态工具筛选、MCP Provider、受控写入/审批与详细管理页面。技术扩展必须经权限和可靠性评估。

## 4. 统一验收口径

- 功能结果带数据来源、范围、统计时间、分析口径和引用信息。
- 业务系统没有足够数据时明确 `partial / INSUFFICIENT_DATA / UNSUPPORTED`。
- 所有数据均继承当前部署平台权限；不得使用服务端管理员凭证绕开原平台授权。
- Adapter A/B/C 仍然只需要实现标准 Catalog 契约；特殊不兼容能力以插件命名空间扩展，不能硬改现有契约语义。
- 新领域必须增加 `02-需求追踪矩阵.md` 的完成状态和契约/模型评估测试。

## 5. 未来需要另外确认的需求

- 模型管理是否需要用量配额/费用分摊/供应商健康路由（当前只有基础配置要求）。
- 管理员是否可在运行中安装/启停插件（当前 V1 仅启动扫描）。
- 是否允许 AI 真正**写入或发布**数据标准、服务、流程（当前需求为推荐与草稿）。
- 有无企业统一知识库、RAG 检索、文件上传后的自动工作流设计（属于既有项目讨论中的候选后续场景，未包含在此次 TXT 的 17 条详细要求中）。
- 是否需跨实例统一监控（可以运维观测，但**不意味着跨产品会话/数据共享**）。
