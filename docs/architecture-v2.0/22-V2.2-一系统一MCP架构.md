# 22 · V2.2 一系统一 MCP 架构

> 状态：Accepted architecture / implementation in progress  
> 生效日期：2026-10-22  
> 决策来源：ADR-027  
> 优先级：本文件覆盖 `21-V2.1-外部MCP业务能力架构.md`、ADR-026 及更早文档中关于跨系统标准业务
> Capability、共享 Domain、产品 Adapter 和 A/B 契约一致性的目标设计；历史验收记录不改写。

## 1. 决策摘要

Product A、Product B、Product C 被视为彼此独立的业务系统。每个系统独立开发、发布和部署一个完整
MCP Server，MCP 内部自行拥有 Tool、Schema、业务语义、权限、Evidence、Prompt/Resource 及原系统 API
集成。平台不再建设跨系统“功能能力层”，也不再要求不同系统提供同名、同结构或同语义的业务 Tool。

`E:\Deep-Agents-AI-Assistant-MCP` 是多个独立 MCP 项目的开发根目录，而不是共享业务领域 Monorepo：

```text
Deep-Agents-AI-Assistant-MCP/
├─ product-a-mcp/
│  ├─ src/
│  ├─ tests/
│  └─ package.json
├─ product-b-mcp/              # Product B 独立维护工单 MCP
└─ product-c-mcp/              # Product C 接入时独立创建
```

不再设置根级 `domains/`、`servers/`、`adapters/`、共享业务契约包或跨产品 Provider 契约测试。若多个 MCP
偶然存在相似代码，先在各 MCP 内独立维护；只有纯技术、无业务语义的组件出现真实复用需求时，才另立决策。

## 2. 平台与业务系统边界

### 主平台 `Deep-Agents-AI-Assistant`

- 身份入口、Session/Run、ContextSnapshot、Agent Runtime、模型、AG-UI/SSE、Web/Embed/SDK。
- MCP Server 连接配置、网络安全、健康状态、Tool 发现、批准快照、Schema 摘要、风险、预算和审计。
- 把经批准的 MCP Tool 机械转换为 LangChain Tool；不解释 Tool 的业务字段、结果、错误或权限名称。
- 不为 Product A/B/C 定义统一 Capability ID、标准业务 Schema、统一结果信封或 Adapter 接口。
- 同一平台发行版可以在不同部署中连接不同 MCP，但不在运行时按产品名做业务分支或聚合路由。
- 可通过经批准的 Platform Extension 扩展纯平台 Tool、Skill 和有限平台 SPI；扩展不得定义业务
  Schema、业务权限或产品 API。Platform Extension 规则见 ADR-028 和 `23-平台扩展机制.md`。

### 每个产品 MCP

- 独占自己的 MCP Tool 名称、输入输出 Schema、业务口径、错误、权限和 Evidence 协议。
- 直接封装所属系统 API，并由所属系统执行最终对象、行、列权限及脱敏。
- 自行决定是否提供 Prompt、Resource 和 Evidence 解析接口；这些内容仍不能自授予平台权限。
- 独立版本、测试、部署、凭证、审计域和故障域；不能依赖另一个产品 MCP 才能启动。

## 3. 发现和批准标识

平台批准只绑定通用 MCP 事实：

```text
serverId + transport endpoint + toolName + input/output schemaDigest + riskLevel
```

平台不要求也不解析 `capabilityId`、`contractVersion`、`requiredPermission` 或跨系统业务命名空间。
`serverId + toolName` 是平台内 Tool 的唯一业务无关定位；MCP 原生 `tools/list` 是该系统 Tool Schema 的
事实来源。Schema 或 Tool 列表变化仍视为漂移，需重新批准并重启形成新快照。

## 4. 调用与安全边界

- Agent 只能生成 MCP Tool Schema 声明的业务参数；用户、租户、权限、Token 和可信标记不得由 Tool
  参数提供。
- 平台基于可信 Run 身份获取短期、audience-bound 的委托凭证，并在传输层发送；凭证不进入 Prompt、
  URL、Tool 参数、持久事件或普通日志。
- MCP 从认证上下文恢复主体，并调用自己的业务系统完成最终授权。平台 MCP allowlist 不能代替业务授权。
- Tool 输出是不可信数据，只能作为 Tool Result；平台限制大小、超时和内容类型，不能把返回文本提升为
  System Prompt。
- Evidence 使用 opaque reference；查看时由产生该引用的 MCP/业务系统按当前主体重新鉴权。

## 5. 主仓旧业务目录的处理

下列目录和组件是 V2.0/V2.1 历史实现，不属于 V2.2 目标发行物：

- `adapters/`
- `domains/`
- `skills/` 中的业务 Skill
- `templates/plugin-bundle-v2/`
- `packages/capability-contracts`、`packages/plugin-sdk`、`packages/plugin-runtime`
- `core/capability` 中面向业务 Catalog/Provider/Executor 的部分

本决策不立即删除它们。默认 Agent Server 切换到 MCP、部署和回归测试改造完成、恢复点确认后，使用独立
清理任务删除源码、workspace 条目、脚本、测试、文档和部署产物。清理完成前，它们只能作为历史回滚
基线，禁止新增业务能力。

## 6. 迁移阶段

### S1：结构纠偏

- MCP 根目录改为“一系统一目录”，Product A 的 Schema 与 Server 合并进 `product-a-mcp/`。
- 删除 MCP 仓共享 `domains/`、`servers/` 分层和跨产品业务元数据。
- 主平台测试不再与旧 Adapter 做业务语义等价比较。

### S2：平台 MCP Host 闭环

- 实现生产 Streamable HTTP、TLS/Host allowlist、重定向/SSRF 防护、委托凭证、连接健康和审计。
- 将当前部署批准的一个 MCP Tool Snapshot 注入 Agent Runtime；不引入产品业务分支。

### S3：按系统接入

- Product A MCP 完成真实 API、权限和 Evidence 重新鉴权。
- Product B 已新增独立 `product-b-mcp/`，提供维护工单 Tool，不依赖 Product A Schema，也不要求
  Tool 或结果结构对齐；当前为 Mock 业务切片。
- 每个系统分别完成契约、安全、故障与部署验收。

### S4：主仓清理

- 默认路径稳定并保留可恢复版本后，独立删除主仓业务目录及旧 Plugin/Capability 机制。
- 更新 Demo、部署、全量测试和历史文档导航；历史验收报告保留并明确为旧架构证据。

## 7. 非目标

- 不建立统一业务 Capability 市场或跨系统领域模型。
- 不让一个 MCP 动态代理或路由到多个业务系统。
- 不要求 Product A/B 提供一致 Tool、结果字段、单位或错误码。
- 不把产品 MCP 合并进主平台进程，也不让 MCP 承担 Agent Session、模型或 UI。
- 不在替代路径未通过验证时直接删除主仓历史业务代码。
