# 插件化能力扩展实施计划

> 状态：E0～E5 已完成
> 日期：2026-10-20
> 适用基线：`docs/architecture-v2.0/` 与当前 M0～M5 已实现代码  
> 定位：V2.0 完成后的架构演进计划；阶段编号使用 E0～E5，避免与既有 M0～M5 混淆

## 1. 背景与问题

当前工程已经实现可信插件目录发现、Manifest 校验、Provider 注册、Capability Executor、Tool Factory 和 Deep Agents 自动装配。安装不同 Product Adapter 后，Agent Server 可以在不修改 Agent Factory 和 UI 的情况下获得不同 Provider。

但当前扩展模型仍是“**封闭 Capability Catalog + 可插拔 Provider**”：

- `KnownCapabilityContract` 是 Core 中固定的 TypeScript 联合类型；
- `standardCapabilityContracts` 在 Core 编译期静态列举；
- `implementCapability()` 只接受 Core 已知契约；
- Plugin Runtime 拒绝 Manifest 中未进入 Catalog 的能力；
- 新增一项标准能力通常需要修改 Core 契约、多层导出、两个 Adapter 和 Manifest，再重新构建整套工程。

因此，当前机制满足“替换某个已知能力的产品实现”，但尚未满足：

> 开发一个能力插件包，安装到当前部署并重启后，系统自动发现契约、Provider、Tool 和可选 Skill，Agent 即可使用；无需修改 Core、Agent Server、Agent Runtime 或 UI。

## 2. 演进目标

### 2.1 目标体验

一个可安装能力包可以包含：

```text
metadata-query-plugin/
├── plugin.json
├── dist/
│   └── index.js
└── skills/
    └── metadata-query/
        └── SKILL.md
```

目标安装流程：

```text
开发并构建 Plugin Bundle
  → 安装到受信任 PLUGINS_DIR
  → 重启 Agent Server
  → 校验来源、路径、哈希、协议与权限声明
  → 注册 Capability Contract
  → 注册 Provider
  → 生成 LangChain Tool
  → 加载可选 Skill
  → Deep Agents 获得新能力
```

新增普通能力时，不应再修改：

- `core/capability` 中的具体能力列表；
- Agent Server Composition Root；
- Agent Runtime / Tool Factory；
- Assistant Web / Embed；
- Deep Agents Agent Loop。

### 2.2 保留的企业约束

“安装一个插件即可增加能力”不代表插件可以绕过企业治理。以下能力仍由平台 Core 和服务端强制执行：

- 当前用户和租户身份由可信服务端建立；
- 每次 Tool Call 执行权限、对象范围和风险策略检查；
- 原业务 API 最终执行行、列、对象权限和脱敏；
- 输入、输出和统一 `CapabilityResult` Schema 校验；
- Evidence 生成、引用、二次鉴权与 Audit；
- 插件批准来源、路径防逃逸、构建产物哈希和协议版本校验；
- 重复能力、未知权限、风险等级不匹配和契约冲突失败关闭；
- Prompt、Skill 和页面 Context 不构成授权依据。

## 3. 扩展模型

### 3.1 Skill、Tool 与 Plugin 的职责

| 扩展项        | 用途                                                 | 是否执行代码 | 是否可授予权限           | 推荐场景                   |
| ------------- | ---------------------------------------------------- | ------------ | ------------------------ | -------------------------- |
| Skill         | 教 Agent 何时、按什么流程使用已有 Tool               | 否           | 否                       | 工作流、领域说明、分析规范 |
| Tool          | 可被模型调用的结构化函数                             | 是           | 否                       | 已有受控运行时中的单一动作 |
| Plugin Bundle | 打包契约、Provider、Tool、可选 Skill、配置和生命周期 | 是           | 只能声明，授权由平台决定 | 新业务集成和可安装能力     |

Skill 只能指导 Agent 使用已有能力。凡是需要访问业务数据、凭证、网络或执行动作的扩展，都必须通过受控 Tool/Plugin，并经过 Capability Executor。

### 3.2 双层 Capability 模型

#### 平台标准能力

用于需要跨产品保持同名、同义、同输入输出语义的能力，例如：

- `data_map.search_objects`
- `data_map.get_object_metadata`
- `data_quality.get_trend`

标准契约从 Core 的固定列表迁移到独立、版本化的契约包，例如：

```text
packages/capability-data-map/
packages/capability-data-quality/
```

不同 Product Adapter 必须引用同一个标准契约包，并通过同一组契约一致性测试。插件不能用自带 Schema 覆盖同 ID、同版本的平台标准契约。

#### 部署私有能力

用于当前组织或产品独有、尚未形成平台标准语义的能力，例如：

```text
acme.order.get_risk_summary
product_a.asset.calculate_score
```

私有能力可以由可信插件携带契约，但必须使用批准的命名空间。经过跨产品验证后，可通过独立 ADR 和迁移流程晋升为平台标准能力。

## 4. 目标接口草案

以下代码仅定义本项目自研接口方向，不代表 Deep Agents 官方 API。实施时以当前 TypeScript 类型、Zod 和实际运行测试为准。

```ts
const metadataQueryV1 = defineCapability({
  id: "data_map.get_object_metadata",
  version: "1.0.0",
  description: "查询已授权业务对象的标准元数据。",
  requiredPermission: "data_map:read",
  riskLevel: "read",
  inputSchema: z.object({
    objectId: z.string().min(1),
    includeColumns: z.boolean().optional(),
  }),
  dataSchema: z.object({
    id: z.string(),
    type: z.string(),
    name: z.string(),
    description: z.string().optional(),
    columns: z
      .array(
        z.object({
          name: z.string(),
          dataType: z.string(),
          description: z.string().optional(),
        }),
      )
      .optional(),
  }),
});

export default definePlugin({
  capabilities: [
    implementCapability({
      contract: metadataQueryV1,
      async execute(input, context) {
        // 调用原业务 API，并映射标准 Result/Evidence。
      },
    }),
  ],
  skills: ["./skills/metadata-query"],
});
```

目标 Manifest V2 草案：

```json
{
  "manifestVersion": "2",
  "id": "metadata-query",
  "name": "Metadata Query Plugin",
  "version": "1.0.0",
  "apiVersion": "2",
  "runtime": {
    "type": "local",
    "entry": "./dist/index.js"
  },
  "capabilities": [
    {
      "id": "data_map.get_object_metadata",
      "contractVersion": "1.0.0",
      "contractSource": "@assistant/capability-data-map",
      "requiredPermission": "data_map:read",
      "riskLevel": "read"
    }
  ],
  "skills": ["./skills/metadata-query"]
}
```

Manifest 只是声明，运行时加载的契约、Provider 和 Skill 必须与 Manifest 完全一致。

### E0：决策固化与回归基线

#### 目标

明确动态契约注册的边界，建立改造前可重复的回归基线，避免演进过程中破坏现有 M0～M5 能力。

#### 工作包

1. 新增 ADR，记录从“静态 Catalog”演进为“稳定 Core + 可信动态契约注册”。
2. 明确首版只支持可信本地插件；HTTP 插件只引用已安装标准契约，不允许远端响应临时定义 Tool Schema。
3. 确定标准能力和私有能力的命名空间、版本、冲突与晋升规则。
4. 恢复或重建最小自动化测试入口，覆盖当前两项能力、A/B Adapter、Manifest V1 和 Tool Factory。
5. 保存现有插件启动日志、工具名称、标准结果和权限拒绝行为作为兼容基线。

#### 安全门禁

- 不改变当前授权、ContextSnapshot、Evidence 和 Audit 行为。
- 不加载任何未经批准的新插件代码。
- 不恢复插件市场、任意上传或热加载。

#### 退出条件

- ADR Accepted；
- 当前 V1 插件回归测试可重复执行；
- 动态契约的信任边界、命名空间和兼容策略无未决项；
- `pnpm lint`、`pnpm typecheck`、`pnpm build` 通过。

### E1：开放 Capability SDK 与动态 Catalog

#### 目标

解除 `KnownCapabilityContract` 对具体能力的封闭枚举，同时保留插件内部完整的 TypeScript/Zod 类型推导。

#### 工作包

1. 在 Plugin SDK/Core 公共接口中增加通用 `defineCapability()`。
2. 将 `implementCapability<Contract extends KnownCapabilityContract>` 调整为面向通用 `CapabilityContract` 的泛型约束。
3. 将 `CapabilityCatalog` 从构造时静态列表扩展为受控 `register/registerMany`。
4. 注册时校验 `id + version` 唯一性、Schema、权限、风险等级和来源元数据。
5. 保留现有 `standardCapabilityContracts` 兼容入口，使 Manifest V1 插件继续工作。
6. Tool Factory 继续只消费 Catalog 与 Registry，不感知具体能力 ID。

#### 重点验证

- 一个测试插件可以声明编译期未知的新能力并保持输入输出类型推导；
- 未注册契约的 Provider 仍然失败关闭；
- 相同 `id + version`、不同 Schema 不允许覆盖；
- Tool 名称归一化冲突可以稳定诊断；
- 现有 A/B 插件行为不变。

#### 退出条件

- Core 不再通过固定联合类型决定所有可扩展能力；
- 动态 Catalog 测试、兼容测试和负面测试通过；
- 尚未开放 Plugin Bundle 自带契约安装，E1 只完成内核能力。

### E2：Plugin Bundle V2 与事务式装载

#### 目标

使一个受信任插件包能够同时贡献 Contract 和 Provider，并保证任何一步失败时都不会留下半注册状态。

#### 工作包

1. 定义并实现 Manifest V2，同时保留 Manifest V1 读取兼容。
2. 增加 `contractSource`、权限、风险、命名空间和可选 Skill 路径声明。
3. Local Plugin Loader 加载插件后先验证契约集合，再注册 Provider。
4. 装载顺序固定为：

   ```text
   discover → validate artifact → load → inspect contract
   → authorize declaration → register contract → register provider
   → verify capability set → initialize → ready
   ```

5. 使用事务或 staging registry；任一步失败时回滚本插件的 Contract、Provider 和状态记录。
6. 插件状态 API 增加契约来源、命名空间、风险和失败阶段等安全诊断字段。

#### 安全门禁

- 入口、契约模块和 Skill 路径都必须位于插件真实根目录内，拒绝符号链接和路径逃逸；
- Manifest 声明、运行时导出和批准策略必须一致；
- 不允许插件覆盖系统保留命名空间或已有标准契约；
- 未批准权限或风险等级直接阻止插件进入 ready；
- 插件模块仍视为可信同进程代码，不宣称沙箱隔离。

#### 退出条件

- 安装一个包含全新私有能力的 V2 插件并重启后，Catalog、Registry 和 Tool 集合自动变化；
- 删除该插件并重启后，能力消失；
- 失败插件不会污染 Catalog 或 Registry；
- V1 插件继续可加载。

### E3：Plugin Skill 自动发现与 Tool 关联

#### 目标

让 Plugin Bundle 可携带 Skill，使 Agent 不仅获得 Tool，还知道何时和怎样可靠使用该 Tool。

#### 工作包

1. Manifest V2 支持一个或多个插件内 Skill 目录。
2. Plugin Runtime 输出已验证的 Skill 描述，Agent Runtime 使用 Deep Agents 官方 Skills 装配点加载。
3. 建立 Skill 与 Capability 的可选关联：Skill 可以声明所需 Tool，但不能授予权限。
4. 缺少所需 Tool、凭证、配置或运行条件时，该 Skill 不进入当前 Agent 的可用集合。
5. 明确 Skill Snapshot：当前 Run/Agent 创建后插件变化不影响进行中的执行；首版仍要求重启生效。
6. 防止 Skill 名称冲突，并记录来源、版本和覆盖规则。

#### 安全门禁

- Skill 文本和外部引用均按不可信指令处理；
- Skill 不得修改权限、主体身份、凭证引用和服务端策略；
- Skill 声明的 Tool 必须属于当前插件或明确批准的依赖；
- 不把 Skill 内容当作已验证业务事实或 Evidence。

#### 退出条件

- 安装一个 Plugin Bundle 后，新的 Tool 和关联 Skill 同时可用；
- 移除或禁用 Tool 时关联 Skill 不再误导 Agent 调用；
- 权限不足时即使 Skill 指示调用，Executor 仍稳定拒绝；
- Tool/Skill 来源可以在诊断信息中追溯。

### E4：标准能力包拆分与现有 Adapter 迁移

#### 目标

把具体标准业务能力从 Core 静态列表迁移到独立版本化契约包，验证“Core 稳定、标准语义可复用、产品实现可替换”。

#### 工作包

1. 建立标准能力包，初始至少包含：

   ```text
   @assistant/capability-data-map
   @assistant/capability-data-quality
   ```

2. 迁移 `data_map.search_objects@1.0.0` 和 `data_quality.get_trend@1.0.0`，保持 ID、Schema 和语义兼容。
3. Product A/B Adapter 改为引用标准能力包，不再依赖 Core 中的具体能力联合类型。
4. 建立每个标准能力包的共享契约测试套件，所有声明支持该能力的 Adapter 必须通过。
5. 选择 `data_map.get_object_metadata@1.0.0` 作为首个通过新机制增加的标准能力。
6. 将元数据字段权限、敏感字段脱敏、对象级授权、Evidence 和 `partial` 语义写入契约与测试。
7. 提供旧导出的过渡兼容层，并给出明确废弃周期。

#### 重点验证

- A/B 原始字段不同，但输出相同标准语义；
- 只安装 A 或 B 插件时均无需修改 Agent Runtime；
- 未实现新能力的部署返回 `UNSUPPORTED`，不伪装为空数据；
- 同名不同义、版本不兼容和单位冲突稳定失败；
- 敏感列无权时不进入模型上下文。

#### 退出条件

- 新增元数据查询能力时未修改 Core、Agent Server、Tool Factory 和 UI；
- 两个 Adapter 通过同一标准契约测试；
- 旧能力调用兼容，迁移与回滚路径明确。

### E5：系统验收、发布流程与文档收口

#### 目标

证明插件化能力扩展可以作为稳定开发模式交付，而不只是单个 POC。

#### 工作包

1. 建立 Plugin Bundle 脚手架或模板，包含 Manifest、Capability、Provider、Skill、README 和测试入口。
2. 建立构建、哈希、批准、安装、升级、禁用、回滚和诊断操作流程。
3. A/B 独立部署分别安装对应插件包，验证相同标准能力和不同私有能力。
4. 验证插件升级时的契约版本兼容、配置迁移和失败回滚。
5. 执行权限、路径逃逸、哈希篡改、Schema 不一致、重复 Tool 名、Skill/Tool 不一致和 Evidence 越权等负面测试。
6. 更新架构文档、插件开发指南、实施状态和验收报告。
7. 如涉及生产试点，再单独验证企业 IdP、真实业务 API、持久化 Repository、官方持久化 Checkpointer、密钥管理和监控告警；Mock 结果不得冒充生产集成。

#### 系统验收场景

```text
场景 A：只新增 Skill
结果：Agent 获得新的工作方法，但 Tool 与权限集合不变。

场景 B：安装私有能力插件
结果：重启后出现新 Contract、Provider、Tool 和可选 Skill；不修改平台代码。

场景 C：安装标准能力 Adapter
结果：不同产品实现相同契约，Agent 和 UI 零修改。

场景 D：插件声明高风险或未知权限
结果：插件不能进入 ready，Tool 和 Skill 均不可见。

场景 E：插件输出 Schema 或 Evidence 不合格
结果：Executor 拒绝把结果作为有效业务数据交给模型。
```

#### 退出条件

- 从插件模板创建一个全新能力到安装可用，不修改平台 Core/Server/Runtime/UI；
- 完整质量门禁和安全负面测试通过；
- 安装、升级、回滚和故障诊断均有真实记录；
- 文档明确真实集成与 Mock 边界；
- 形成最终验收报告并由负责人批准。

## 6. 预计主要影响范围

| 模块                      | 主要变化                                            | 不应承担的变化             |
| ------------------------- | --------------------------------------------------- | -------------------------- |
| `core/capability`         | 通用 Contract、动态 Catalog、统一 Result/Evidence   | 继续枚举所有具体业务能力   |
| `core/policy`             | 通用资源目标提取、权限和风险策略                    | 信任插件自行批准权限       |
| `packages/plugin-sdk`     | `defineCapability()`、开放泛型、Skill 声明          | 直接依赖 Deep Agents       |
| `packages/plugin-runtime` | Manifest V2、事务注册、Contract/Provider/Skill 校验 | 插件市场、在线下载、热加载 |
| `packages/agent-runtime`  | 消费已验证 Tool 与 Skill 集合                       | 重写 Agent Loop 或产品分支 |
| `adapters/*`              | 引用标准契约包，实现业务映射                        | 自定义同名标准语义         |
| `apps/agent-server`       | 组合新 Runtime 输出和诊断信息                       | 按 Capability ID 手写路由  |
| `packages/assistant-ui`   | 默认无需修改；只渲染标准 View                       | 执行插件提供的任意 HTML/JS |

## 7. 兼容、迁移与回滚

### 7.1 兼容原则

- Manifest V1 与 V2 至少并行一个迁移周期；
- 现有能力 ID、工具名称和 Result Schema 不无故变化；
- 旧静态 Catalog 可以在 E1～E3 作为兼容来源，与动态来源使用同一冲突规则；
- 当前部署未安装 Provider 时继续返回不可重试 `UNSUPPORTED`；
- 进行中的 Run 使用创建时固定的 Tool/Skill Snapshot。

### 7.2 迁移顺序

```text
先开放 SDK/Catalog
→ 再支持 Manifest V2
→ 再挂载 Plugin Skill
→ 再迁移现有标准能力
→ 最后删除废弃静态入口
```

禁止在同一个阶段同时删除旧入口、迁移全部 Adapter 和改变运行协议。

### 7.3 回滚策略

- E1：恢复 Catalog 静态初始化和旧泛型约束；无数据迁移。
- E2：关闭 Manifest V2，只加载 V1；移除对应插件安装包并重启。
- E3：关闭插件 Skill 装配，保留 Tool；不影响 Capability 执行。
- E4：Adapter 临时恢复引用旧兼容导出；契约 ID/版本保持不变。
- E5：按部署包版本和插件哈希回滚，不跨实例共享状态。

## 8. 风险与控制

| 风险                   | 后果                              | 控制措施                                                     |
| ---------------------- | --------------------------------- | ------------------------------------------------------------ |
| 插件自定义同名契约     | 跨产品同名不同义                  | 标准命名空间保留；同 ID/版本按 Schema 指纹校验               |
| 插件虚报权限或低报风险 | 越权或绕过审批                    | 权限允许列表、风险策略、安装审批；声明不等于授权             |
| 动态加载恶意代码       | 同进程数据或凭证泄露              | 仅加载可信批准产物、哈希校验、最小 Host Services；不宣称沙箱 |
| Skill Prompt Injection | Agent 被诱导越权或忽略规则        | Skill 只提供指令；Executor 和业务 API 始终强制授权           |
| 半注册状态             | Tool、Contract 和 Provider 不一致 | staging registry、事务提交、失败回滚                         |
| Tool 数量过多          | 模型选择困难、上下文膨胀          | 按部署、权限、领域和 Skill 需求筛选；后续再评估 Tool Search  |
| 动态 Schema 破坏兼容   | 运行时失败或旧会话不一致          | 契约版本、Schema 指纹、启动校验、Run Snapshot                |
| 为追求易扩展弱化标准化 | Adapter 重新暴露产品差异          | 标准能力包、共享契约测试、私有命名空间和晋升流程             |

## 9. 明确不做

本计划不包含：

- 插件市场、在线搜索和自动下载安装；
- 任意用户上传 JavaScript 并立即执行；
- 不重启热加载；
- 插件间任意依赖解析和包管理器；
- 通用 IM/多渠道 Gateway；
- 跨 A/B/C 实例会话、凭证或模型配置同步；
- 让 Skill 替代 Tool、Policy、业务权限或 Evidence；
- Fork 或重写官方 Deep Agents Agent Loop、LangGraph 状态机制。

## 10. 全阶段质量门禁

每个阶段至少执行：

```text
pnpm lint
pnpm typecheck
pnpm build
```

建立测试命令后还必须执行相应单元、契约、集成与系统测试。缺少真实模型 Key、真实企业 IdP 或真实业务 API 时，必须分别记录 Mock、Test Double 和 Not Run，不能用模拟结果宣称生产集成成功。

任何 Capability 契约、权限、Evidence 或插件信任边界变化，都必须同步更新：

- `docs/implementation-status.md`
- `docs/architecture-v2.0/18-架构决策记录.md`
- 当前阶段验收报告

## 11. 总体完成定义

全部 E0～E5 完成后，应达到：

1. 一个可信 Plugin Bundle 可以携带新 Contract、Provider、Tool 和可选 Skill。
2. 安装插件并重启即可让 Agent 获得新能力，不修改平台 Core、Server、Runtime 或 UI。
3. 平台标准能力在不同产品 Adapter 中保持同名、同义和同契约。
4. 私有能力受命名空间、权限、风险和来源治理约束。
5. Skill 只指导 Tool 使用，不构成授权依据。
6. 每次调用继续经过服务端权限、原业务权限、输出校验、Evidence 和 Audit。
7. 现有 Manifest V1 和两项标准能力完成平滑迁移，并具备明确回滚路径。
8. 整个演进没有把项目扩大为 OpenClaw 式插件市场或任意代码平台，也没有重写 Deep Agents。
